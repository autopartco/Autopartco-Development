# v2.0.0: búsqueda, publicidad, inicio y rendimiento

Versión: **v2.0.0** (última publicada `v1.7.4`). Incluye el perfil de almacén v2 (`2026-11-11-perfil-almacen-v2-plan.md`) más este plan. Rama: `feature/perfil-almacen` continúa; las tareas de este plan van en `feature/busqueda-v2`, `feature/publicidad`, `feature/inicio-v2` y `feature/rendimiento-redis`, todas desde `develop`. Secuencia por tarea: `database` → `backend` → `frontend` → `qa-seguridad`.

## Objetivo y alcance

Entra:
1. **Búsqueda v2:** texto libre («pastillas de freno spark 2015 bogota»), tolerante a errores y tildes, con relevancia, más filtros, facetas con conteos, autocompletado y orden por cercanía.
2. **Publicidad:** el almacén crea campañas para sus productos, paga por publicarlas (Wompi) y ve estadísticas de cada campaña.
3. **Inicio `/` v2:** conserva el mapa de cobertura; más llamativo, explica qué es Autopartco y cómo funciona, lleva directo a productos y capta vendedores.
4. **Rendimiento:** Redis como caché compartida y limitador distribuido, caché HTTP (ETag, `Cache-Control`) y cookies funcionales.

No entra: motor externo de búsqueda (Elasticsearch, Meilisearch, Algolia), subasta en tiempo real o costo por clic, publicidad fuera de Autopartco, renderizado en servidor (SSR), PWA sin conexión.

## Estado actual (hallazgos)

- **Búsqueda:** `ProductBrowseController.published` trae **todos** los listados publicados (`ListingQueries.publishedListings`), filtra texto, categoría, almacén y sucursal en Java, deja un resultado por producto (`cheapestPerProduct`) y pagina en memoria (`Paging.slice`). El texto solo exige que todas las palabras aparezcan en el nombre, SKU, referencia o fabricante. El costo crece con todo el catálogo en cada búsqueda.
- **BD:** ya tiene `pg_trgm`, `unaccent` e `immutable_unaccent`. No tiene PostGIS.
- **Ubicación:** en `develop` (sin integrar en esta rama) ya existen `BranchMapQueries` (Haversine en SQL, sedes más cercanas), `GET /marketplace/branches/map`, `SlidingWindowRateLimiter` (en memoria), `maplibre-gl` y `CoverageMap` en el hero del inicio, y un selector de área en la cabecera (`useMapArea`).
- **Precios:** `promotions` son descuentos de precio, no publicidad. `order_attributions` existe. El cobro por Wompi existe para suscripciones (`SubscriptionCheckout`, `seller_payments`, `SubscriptionWompiHandler`; sandbox = producción).
- **Caché:** no hay Redis ni `@Cacheable`. Solo el catálogo de vehículos (1 h + ETag) y fabricantes del almacén usan `Cache-Control`. `SettingsQueries` cachea 30 s por instancia. El frontend no tiene librería de caché de datos.
- **Cookies:** solo el refresh token (`RefreshCookie`).
- **El perfil v2 se escribió con Leaflet:** como `develop` ya usa MapLibre, T5 del plan de perfil debe usar `maplibre-gl` y `features/location` (sin dependencias nuevas).

## Contratos

### 1. Búsqueda v2

#### Datos (Supabase)

```sql
create table search_listings (
  listing_key text primary key,              -- '<productId>:<branchId>'
  product_id uuid not null references products(id) on delete cascade,
  branch_id uuid not null references branches(id) on delete cascade,
  store_id uuid not null references store(id),
  category_id uuid null, category_path uuid[] not null default '{}',   -- la categoría y sus ancestros
  manufacturer_id uuid null,
  name text not null, price numeric(14,2) not null, stock int not null, has_promotion boolean not null default false,
  city_code char(5) null, department_code char(2) null,
  latitude double precision null, longitude double precision null,
  store_rating numeric(2,1) null, universal boolean not null default false,
  vehicle_make_ids uuid[] not null default '{}', vehicle_model_ids uuid[] not null default '{}', vehicle_version_ids uuid[] not null default '{}',
  year_from smallint null, year_to smallint null,
  document tsvector not null,   -- A: nombre, referencia, SKU; B: fabricante, categoría; C: vehículos; D: descripción, atributos
  search_text text not null,    -- immutable_unaccent(lower(nombre + fabricante + categoría + referencia))
  published_at timestamptz not null, updated_at timestamptz not null default now()
);
create index ix_sl_document on search_listings using gin (document);
create index ix_sl_trgm on search_listings using gin (search_text gin_trgm_ops);
create index ix_sl_category on search_listings using gin (category_path);
create index ix_sl_vehicle_models on search_listings using gin (vehicle_model_ids);
create index ix_sl_geo on search_listings (latitude, longitude) where latitude is not null;
create index ix_sl_price on search_listings (price);
create index ix_sl_product on search_listings (product_id);
create table search_synonyms (term text primary key, expands_to text[] not null);  -- 'bandas' → {'pastillas'}
create table search_suggestions (term text primary key, kind varchar(20) not null, weight int not null default 0);
create index ix_ss_trgm on search_suggestions using gin (term gin_trgm_ops);
-- RLS habilitado en las tres tablas (solo el backend accede).
```

- El backend mantiene `search_listings` con un **upsert al confirmar la transacción** de producto, inventario, precio, promoción, sucursal o estado del almacén (eventos de dominio, `AFTER_COMMIT`), más una **reconstrucción completa** programada cada noche y bajo demanda (`POST /api/v1/admin/search/reindex`, solo ROOT).
- Se descartan los triggers de BD: la lógica de lo publicado (`ListingQueries`) vive en Java y duplicarla en SQL las separaría.
- `search_suggestions` se carga con nombres de categorías, fabricantes, marcas y modelos, y con búsquedas frecuentes con resultados (`marketplace_searches`, últimos 30 días, ≥3 sesiones).

#### Interpretación de la consulta (`QueryParser`)

1. Normaliza: minúsculas, sin tildes, espacios simples. Tope de 120 caracteres.
2. Reconoce años (`19xx|20xx`), marcas y modelos (diccionario del catálogo, también con un error de una letra), ciudades (DIVIPOLA) y referencias tipo `[A-Z0-9-]{5,}`.
3. Lo reconocido se vuelve filtro **sugerido**, no obligatorio. La respuesta lo devuelve en `interpreted` y el frontend muestra chips que se pueden quitar.
4. El resto del texto se expande con sinónimos y se busca con `websearch_to_tsquery('spanish', …)`, con prefijo en la última palabra.
5. Si hay 0 resultados, se repite con similitud de trigramas (`search_text % :q`, umbral 0.3) y se responde `fuzzy: true` («Mostrando resultados parecidos a…»).

#### API

`GET /api/v1/marketplace/search`:

| Parámetro | Tipo | Nota |
|---|---|---|
| `q` | texto | opcional |
| `categoryId` | uuid | incluye subcategorías |
| `manufacturerId` | uuid[] | multivalor |
| `makeId`, `modelId`, `versionId`, `year` | | vehículo; `year` cruza con `year_from/to` |
| `priceMin`, `priceMax` | COP | |
| `inStock` | bool | |
| `onSale` | bool | con promoción vigente |
| `storeId`, `branchId` | uuid | |
| `cityCode`, `departmentCode` | DIVIPOLA | |
| `lat`, `lng`, `radiusKm` | | 1–200; sin radio solo ordena por cercanía |
| `minRating` | 1..5 | |
| `universal` | bool | |
| `sort` | `relevance` (por defecto) \| `price_asc` \| `price_desc` \| `nearest` \| `newest` \| `rating` | `nearest` exige `lat/lng` → si faltan, 400 `LOCATION_REQUIRED` |
| `page`, `size` | | `page` desde 0; `size` 1..48 |
| `facets` | bool | por defecto true en la primera página |

Respuesta:
```json
{ "items": [ { "...ProductResponse": "", "distanceKm": 3.2, "sponsored": false, "adImpressionToken": null } ],
  "page": 0, "size": 24, "total": 312, "fuzzy": false,
  "interpreted": { "text": "pastillas de freno", "makeId": "uuid", "modelId": "uuid", "year": 2015, "cityCode": "11001" },
  "facets": { "categories": [{"id":"…","name":"Frenos","count":120}], "manufacturers": [...], "cities": [...],
              "price": {"min": 18000, "max": 420000}, "inStock": 280, "onSale": 41 },
  "sponsored": [ { "...ProductResponse": "", "sponsored": true, "adImpressionToken": "…" } ] }
```

- Relevancia: `ts_rank_cd(document, query)` × (1 + 0,3·tiene stock) × (1 + 0,1·calificación/5) × decaimiento por distancia si hay ubicación (`1 / (1 + km/25)`).
- Un resultado por producto: el listado de menor precio **dentro de los filtros** (`distinct on (product_id)` en una subconsulta), como hace hoy `cheapestPerProduct`.
- Cercanía: caja de coordenadas (`lat ± r/111`, `lng ± r/(111·cos lat)`) sobre `ix_sl_geo` y luego Haversine, igual que `BranchMapQueries`.
- Facetas: una consulta con `grouping sets` sobre el mismo `WHERE` sin el filtro de esa faceta. Máximo 20 por grupo.
- Rendimiento: p95 ≤ 150 ms sin caché con 100 000 listados (verificar con `EXPLAIN ANALYZE`), ≤ 20 ms con caché.
- `GET /api/v1/marketplace/products` se mantiene por compatibilidad y pasa a usar el mismo motor internamente. `/search` es el contrato nuevo del frontend.

`GET /api/v1/marketplace/search/suggest?q=pas&lat=&lng=` → `{ "suggestions": [{"term":"pastillas de freno","kind":"QUERY|CATEGORY|MANUFACTURER|VEHICLE"}], "products": [ máx. 4 resultados rápidos ] }`. `q` de 2 caracteres o más, máximo 8 sugerencias, con `Cache-Control: public, max-age=300`.

### 2. Publicidad

#### Modelo comercial

- Se cobra **por publicar**: tarifa diaria por ubicación (prepago), no por clic.
- El almacén elige productos, ubicación, segmentación y fechas. Paga el total por Wompi y la campaña se activa al aprobarse el pago.
- Ubicaciones (`AdPlacement`):

| Ubicación | Dónde aparece | Cupo |
|---|---|---|
| `SEARCH_TOP` | primeras posiciones de búsqueda/categoría cuando la campaña coincide con la consulta, la categoría o el vehículo | 2 por página |
| `HOME_FEATURED` | carrusel «Destacados» del inicio | 12 rotativos |
| `CATEGORY_TOP` | cabecera de la página de categoría | 3 |
| `PRODUCT_RELATED` | «También te puede servir» en el detalle de producto | 4 |

- Tarifas en `ad_placement_prices` (COP por día, editables por el admin). Valores iniciales sugeridos: `SEARCH_TOP` 15 000, `HOME_FEATURED` 25 000, `CATEGORY_TOP` 12 000, `PRODUCT_RELATED` 8 000. Total = tarifa × días × ubicaciones. Precios con IVA incluido: confirmar con contabilidad (riesgo).
- Si hay más campañas activas que cupos, rotan con peso uniforme y tope de frecuencia (el mismo visitante ve el mismo anuncio máx. 3 veces por hora en esa ubicación). No hay subasta.
- Reglas: solo productos publicados del almacén, de 1 a 20 productos por campaña, duración de 1 a 90 días, inicio desde hoy y hasta 60 días adelante. El almacén necesita suscripción activa. Si el producto deja de estar publicado, el anuncio deja de mostrarse **sin reembolso automático** (se informa en el formulario). El admin puede pausar o rechazar una campaña; si la rechaza antes de empezar, se marca «reembolso pendiente» y el reembolso es manual.
- Etiqueta visible «Patrocinado» en todos los anuncios (obligatoria; Ley 1480, información al consumidor).

#### Datos (Supabase)

```sql

  targeting jsonb not null default '{}',   -- {keywords[], categoryIds[], makeIds[], modelIds[], cityCodes[]}
  total_price numeric(14,2) not null, paid_at timestamptz null, rejected_reason varchar(300) null,
```

#### API del portal (`STORE_UPDATE` para escribir, `ANALYTICS_READ` para estadísticas)

- `GET /api/v1/stores/{storeId}/ads/prices` → `[{ placement, dailyPrice }]`.
- `POST /api/v1/stores/{storeId}/ads/campaigns` `{ name, productIds[], placements[], startsOn, endsOn, targeting }` → 201 `AdCampaign` en `DRAFT`, con `totalPrice` calculado.
  - Errores 400: `AD_PRODUCT_NOT_PUBLISHED`, `AD_INVALID_DATES`, `AD_TOO_MANY_PRODUCTS`.
  - 409 `SUBSCRIPTION_INACTIVE`.
- `PUT` y `DELETE` sobre `…/campaigns/{id}`: solo en `DRAFT`. `GET …/campaigns?status=` lista.
- `POST …/campaigns/{id}/checkout` → `CheckoutResponse` igual que la suscripción (Wompi, referencia `ADS-…`). La campaña pasa a `PENDING_PAYMENT`. Si el webhook aprueba el pago, pasa a `SCHEDULED` o `ACTIVE`; si se rechaza, vuelve a `DRAFT`.
- `POST …/campaigns/{id}/pause` y `…/resume`: no extienden fechas. `POST …/cancel`: sin reembolso automático.
- `GET …/campaigns/{id}/stats?from&to` → estadísticas de la campaña:
  ```json
  { "impressions": 0, "reach": 0, "clicks": 0, "ctr": 0.0, "whatsappClicks": 0, "addToCart": 0,
    "orders": 0, "revenue": 0, "costPerClick": 0, "roas": 0,
    "daily": [], "byPlacement": [], "byProduct": [] }
  ```
  - `reach`: visitantes diarios distintos.
  - `orders` y `revenue`: pedidos con clic en el anuncio en los 7 días previos, por el mismo visitante o la misma cuenta (`order_attributions`).
  - `costPerClick` = costo ÷ clics. `roas` = ingresos ÷ costo.
- Admin (`ROOT`): `GET /admin/ads/campaigns`, `POST …/{id}/reject {reason}`, `POST …/{id}/pause` y `PUT /admin/ads/prices`.

#### Entrega y eventos

- `AdServer.pick(placement, context, limit)`: candidatos de las campañas `ACTIVE` (caché Redis de 60 s) que coinciden con la segmentación. Excluye productos ya mostrados en la página y respeta el tope de frecuencia.
- Cada anuncio lleva `adImpressionToken`, firmado con HMAC (`campaignId|productId|placement|day|exp`) y válido 30 min.
- `POST /api/v1/events/ads` `{ token, kind: IMPRESSION|CLICK|WHATSAPP_CLICK|ADD_TO_CART, anonymousId }` → 204 siempre.
  - Las impresiones se envían en lote cuando el anuncio es visible ≥50 % durante ≥1 s.
  - Un token falso o vencido se ignora. Mismo límite por IP que `/events/visibility`.
  - `ORDER` lo registra el backend al pagar el pedido.

### 3. Inicio `/` v2

Seguir `docs/design/AUTOPARTCO_DESIGN_SYSTEM.md` (§17 y §20.15). Secciones, en orden:

1. **Hero:**
   - Propuesta en una frase («Encuentra el repuesto exacto para tu carro, en almacenes cerca de ti»).
   - Buscador grande con sugerencias y selector de vehículo en línea («¿Qué carro tienes?»).
   - Chips de búsquedas populares y el **mapa de cobertura actual (`CoverageMap`)** al lado (debajo en móvil), con el conteo de almacenes y repuestos en el área.
2. **Acceso directo a productos:** categorías con ícono y un carrusel «Cerca de ti», ordenado por cercanía al área elegida (`/search?sort=nearest`).
3. **Cómo funciona:** 3 pasos (buscar por vehículo, comparar precios y almacenes, comprar o cotizar por WhatsApp). Reutiliza `how-it-works.tsx`.
4. **Destacados:** anuncios `HOME_FEATURED` con la etiqueta «Patrocinado» y relleno orgánico si sobran cupos.
5. **Qué es Autopartco:** cifras reales de la plataforma (almacenes, ciudades, repuestos) desde `PlatformStats`, más garantías (pago seguro Wompi, almacenes verificados, reseñas).
6. **Para vendedores:** bloque de captación con beneficios, planes y CTA «Registrar mi almacén» (`/vender`), y testimonio o cifra de visibilidad si hay datos.
7. **Comparación de precios** (`price-comparison.tsx` actual), si aporta. Si no, se retira.

Criterios: LCP ≤ 2,5 s en 4G simulado; el mapa carga diferido y no bloquea el LCP; sin scroll horizontal a 360 px; cada sección con encabezado `h2` y estados vacío y de error.

Se agrega `GET /api/v1/marketplace/home` → `{ stats, popularSearches[], categories[], nearby[], featured[] }` en una sola llamada, con caché de 60 s por área redondeada a 0,1°.

### 4. Rendimiento: Redis, caché HTTP y cookies

#### Redis (`shared/cache`)

- `spring-boot-starter-data-redis` (Lettuce) + `spring-boot-starter-cache`. La URL va en `REDIS_URL` del `.env` raíz.
- Si `REDIS_URL` falta o Redis no responde, se usa una caché local Caffeine y un limitador en memoria: **la app nunca falla por Redis**. Tiempos de espera: conexión 500 ms, comando 200 ms.

| Caché | Clave | TTL | Invalidación |
|---|---|---|---|
| `catalog:options` (categorías, fabricantes, vehículos) | fija | 1 h | evento de cambio en catálogo |
| `search:results` | `v{catalogVersion}:sha256(parámetros normalizados + grupo de precio del comprador)` | 60 s | sube `catalogVersion` en cada upsert de `search_listings` (se agrupan en 5 s) |
| `search:suggest` | `q` normalizado | 5 min | reindexación |
| `store:profile`, `store:branches` | `storeId` | 5 min | evento al cambiar perfil, sucursal, servicio o ajustes |
| `settings:store` | `storeId` | 5 min | evento al guardar (reemplaza la caché local de 30 s de `SettingsQueries`) |
| `home` | área redondeada | 60 s | TTL |
| `ads:active` | `placement` | 60 s | al cambiar estado de una campaña |
| `ads:freq` | `visitorHash:campaign:placement` | 1 h | TTL |
| `ads:impressions` | contador `campaign:product:placement:day` | volcado a `ad_events` cada minuto | — |
| `ratelimit:*` | ventana deslizante por IP y ruta | ventana | — |

- Los precios personalizados (`BuyerContext` con promociones por audiencia) **no se cachean por persona**. La clave usa el grupo de audiencia del comprador; las búsquedas de compradores con promociones individuales no usan caché.
- `SlidingWindowRateLimiter` pasa a Redis (script Lua o `ZSET`) para que el límite valga entre instancias, y se aplica también a `/auth/*` (cierra el pendiente de T2 del plan de perfil: 10 por minuto por IP en login, verificación y reenvío).
- Métricas: aciertos y fallos por caché expuestos en `/actuator/metrics` (solo admin).

#### Caché HTTP

- GET públicos del marketplace (`/search`, `/suggest`, `/home`, perfil y sucursales de tienda, detalle de producto, categorías): `ETag` débil del cuerpo y `Cache-Control: public, max-age=30, stale-while-revalidate=120`. Responden 304 con `If-None-Match`.
- Nunca `public` en respuestas con sesión: `Vary: Authorization, Cookie` o `private`.
- Frontend: `lib/http` guarda en memoria por URL (LRU de 200 entradas) con ETag, revalida al enfocar la ventana y desduplica peticiones en curso.
- Vercel: los recursos con hash usan `Cache-Control: public, max-age=31536000, immutable`; `index.html` usa `no-cache`. Verificar `vercel.json`.

#### Cookies (funcionales; respetan la Ley 1581)

- `ap_area`: área elegida (lat/lng redondeados a 0,01°, código de ciudad). 30 días, `SameSite=Lax`, `Secure`, legible por JS.
  - El backend la usa como ubicación por defecto en `/search` y `/home` cuando no llegan `lat/lng`.
  - Reemplaza el almacenamiento local actual del área.
- `ap_aid`: identificador anónimo de visitante (ya existe en `localStorage`). 1 año, `HttpOnly`, `SameSite=Lax`, `Secure`.
  - Se emite en `/events/*` y lo usan visibilidad y anuncios. El cliente deja de enviar `anonymousId`, que se acepta 90 días por compatibilidad.
- Las dos cookies son funcionales y necesarias para el servicio pedido (cercanía y estadísticas agregadas sin identidad). Se informan en la política de cookies y no requieren aceptación. Las cookies analíticas o de marketing, si se añaden después, sí la requieren.

## Decisiones

- **Postgres FTS + trigramas en vez de motor externo:** las extensiones ya están, el volumen es de cientos de miles de listados y se evita otro servicio que sincronizar y pagar. Si p95 > 300 ms con caché o el catálogo supera 2 M de listados, evaluar Meilisearch con el mismo contrato `/search`.
- **Tabla desnormalizada con upsert desde la app:** las consultas evitan 8 joins; la consistencia se asegura con eventos tras commit y la reconstrucción nocturna. Descartada la vista materializada: el refresco completo bloquea y es lento.
- **Haversine con caja de coordenadas en vez de PostGIS:** suficiente para radios ≤ 200 km en Colombia y ya se usa en `BranchMapQueries`. Descartado PostGIS por ahora (instalarlo es un cambio de infraestructura).
- **Publicidad prepagada por día:** es lo que pidió el usuario («cobrar por publicar»), es predecible para el almacén y no exige una subasta. Descartados el costo por clic (necesita saldo, fraude de clics y conciliación) y el costo por mil impresiones.
- **Token firmado en anuncios:** impide registrar eventos de campañas ajenas o inventadas sin consultar la BD en cada evento.
- **Redis opcional con respaldo local:** el despliegue no se cae si Redis falla y en desarrollo funciona sin Redis.
- **Cookies solo funcionales:** cumplen la Ley 1581 sin banner; los datos de analítica siguen agregados y sin identidad.

## Riesgos y puntos a verificar

- **Proveedor de Redis:** hay que elegir dónde corre (mismo proveedor que el backend para baja latencia; plan gratuito o pago) y quién lo paga. Sin decisión, T8 se entrega con el respaldo local activo.
- **IVA y facturación de la publicidad:** confirmar si la tarifa incluye IVA y si hay que emitir factura electrónica (DIAN) por cada campaña. Por ahora se muestra «IVA incluido» y la factura es manual.
- **Coherencia del índice:** un evento perdido deja un listado desactualizado hasta la reconstrucción nocturna. Monitorear las diferencias entre `search_listings` y los listados publicados (conteo diario).
- **Precios personalizados en caché:** si `BuyerContext` crece (más audiencias), revisar la clave de caché antes de ampliar.
- **Fraude de anuncios:** el token, el límite por IP y la deduplicación mitigan pero no eliminan los bots. Las estadísticas se rotulan «estimadas».
- **Rendimiento real:** medir con datos de `tools/seed` a escala antes de declarar la mejora.
- **Frontend en otra cuenta:** T3, T6 y la parte de frontend de T7 y T8 se ejecutan desde esa cuenta con este documento como contrato.
- **Conflictos:** T2, T5 y T8 tocan `WebSecurityConfig` y `ProductBrowseController`; ejecutarlos en secuencia.
